# STEP7 B: 제한된 의존성 점검·보조 최적화 결과

A와 분리된 브랜치에서 진행했다. **채택 최적화 0건, 삭제 0건.** 코드 ZIP 압축 단계만 3쌍 측정했고 작은 시간 절감과 크기 증가 때문에 변경을 불채택했다. 운영 코드·workflow·전략·증거·예약·커서는 변경하지 않았다. G5A 증거나 신규 경제성과가 아니다.

| 지표 | 기존 level6 | 검토 level1 |
|---|---:|---:|
| wall 중앙값 / 범위, 초 | 0.004607 / 0.004548–0.004619 | 0.004134 / 0.003764–0.004941 |
| CPU 중앙값 / 범위, 초 | 0.004607 / 0.004548–0.004619 | 0.004134 / 0.003764–0.004941 |
| peak RSS 중앙값, MiB | 19.7891 | 19.7852 |
| workflow 파일 읽기 | 9 | 9 |
| JSON 파싱 | 0 | 0 |
| ZIP bytes / MiB | 33,730 / 0.03217 | 37,289 / 0.03556 |

시간 중앙값 절감은 약0.000473초이고 첫 쌍은 오히려 느렸다. ZIP은3,559bytes(+10.55%) 증가한다. RSS의 미세 차이를 실제 메모리 개선이라고 판정하지 않았다. 매 관측은 새 Python 프로세스, 실제 코드9개만 고정 복사한 입력이다. mock/compile/저장 시간을 포함하며 interpreter 시작·복사 준비·검산은 타이머에서 제외했다. peak RSS는 준비를 포함한 전체 worker 최대값이다. root가 경제 재생 전 측정 창을 승인했고 종료 직후 A에 자원을 반환했다.

기능 검산은 합계 PnL이 아니라9개 전체 압축 해제 바이트·경로·파일 크기·권한·고정 시각·압축 방식·파일별 SHA 및 MANIFEST 전체 바이트 동일성이다. 압축 크기 차이만 발생했다. 거래 로직을 실행하거나 바꾸지 않았으므로 신호/차단/점유/청산/비용/미완결/판정/경제 digest에 새로운 결과를 주장하지 않는다.

## 보존 분류

- KEEP_RUNTIME: workflow snapshot9개 코드, registry 및 CLI의 확인된 호출 경로.
- KEEP_REPRO: 기존3개 manifest의 명시적 코드 참조, native6모듈·부모·실행기·회귀시험. 오래됐다는 이유로 제거하지 않았다.
- REMOVE_SAFE: 입증 대상 없음. 작업 소유의 측정 임시 디렉터리는 각 프로세스 종료 때만 정리했다.
- DEFER_UNKNOWN: 전역 registry의 외부 호출, frontend baseline/dist 복구 의존성, 원격 VPS/CF/GS·외부 scheduler 실제 상태. 해당 상태는 미확인이다.

전체 tracked 경로 메타데이터3,058개 중 backend1,682개, frontend72개, workflow609개, development evidence411개를 분류 표면으로 확인했다. 모든 파일 내용을 읽었다는 뜻이 아니다. 실제 점검은 STEP7 코드/CLI/workflow와 manifest3개로 한정했다. 두 archive workflow는 소비자·복구 목적이 같다고 입증되지 않고 보존 기간도30일/90일로 달라 모두 유지한다. 삭제 전제인 소유자·현재 미사용·복구·보호 참조 부재를 모두 만족한 파일은 없다.

변경 파일은 이 디렉터리의 측정/분류/보고 기록뿐이다. frontend canonical 사전 검증은 PASS, 배포 불필요. 구현 diff가 없어 런타임 롤백도 없다. 측정 이력은 삭제하거나 예산을 초기화하지 않는다. 허용3쌍은 소진했으며 추가 benchmark를 실행하지 않는다. B 소유 잔여 실행은 없고 원격 다른 작업은 UNKNOWN으로 보존한다.
